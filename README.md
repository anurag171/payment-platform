# payment-platform

The payment orchestration monolith, decomposed into one Spring Boot 3.4.x / Java 21
microservice per Temporal workflow type and one per activity group — 15 core services,
plus a REST/MQ/Kafka edge (`payment-gateway-service`) and a test-only auto-responder
(`payment-simulator-service`). 17 services total.

**Read §3 before you assume these talk to each other over HTTP — they mostly don't.**

## 0. Can't-skip disclaimer

Same as the monolith this was decomposed from: built in a sandbox with no Maven Central
access, so none of this has been compiled. The mechanical parts (pom.xml, Dockerfile,
k8s manifests, docker-compose.yml) were generated by `_generator/generate_services.py`
from `_generator/services.yaml` and are internally consistent by construction. The
business logic (workflow/activity impls, controllers) is the same code already reviewed
in the monolith, copied in by `_generator/copy_impls.py` and re-verified here for the
task-queue rewiring the split requires. Treat it as a complete, structurally-correct
first draft to compile and fix forward.

## 1. Why 17 services, and the template that produces them

Rather than hand-writing 17 near-identical Maven projects, this is **generated from a
manifest**:

- `_generator/services.yaml` — one entry per service: name, type, task queue, which
  source file(s) it owns, extra Maven dependencies, replica count, resource sizing.
- `_generator/generate_services.py` — reads the manifest, writes each service's
  `pom.xml`, `Dockerfile`, `application.yml`, `Application.java`, `TemporalConfig.java`
  (or `TemporalClientConfig.java` for the two edge services), and `k8s/` manifests.
- `_generator/copy_impls.py` — copies the actual business-logic files from the monolith
  into each generated service and wires up the per-service `TemporalConfig.java` to
  register exactly the one workflow/activity type that service owns.

**This is the reusable template.** Adding an 18th service (say, splitting `booking` out
as its own partner rather than folding it into `partner-activity-service`) means adding
one entry to `services.yaml` and re-running both scripts — not hand-writing a pom.xml.

## 3. How services actually talk to each other — read this before drawing a diagram

**They don't call each other over HTTP.** Every workflow/activity service is a Temporal
*worker*: it connects outbound to the Temporal Frontend Service and polls its own task
queue. When `inbound-normalization-workflow-service` needs to hand off to
`qualification-workflow-service`, it doesn't make an HTTP call to it — it asks the
Temporal server to schedule a child workflow on `QUALIFICATION_TQ`, and whichever
`qualification-workflow-service` pod is polling that queue picks it up. Same for every
activity call. **Temporal itself is the service mesh here** — it does the discovery,
the retry, the timeout, and the load-balancing across replicas of the target service
that a service-to-service HTTP call would otherwise need a mesh for.

This matters for how you read the Kubernetes manifests in this repo:

- **Every service still gets its own `Service` (ClusterIP)** — not because other pods
  call it over HTTP, but because Prometheus needs a stable DNS name to scrape
  `/actuator/prometheus`, and because it's the idiomatic way to `kubectl port-forward`
  or debug one service in isolation. Don't read a Service object here as evidence of a
  planned HTTP caller.
- **Only two services have an inbound HTTP surface at all**: `payment-gateway-service`
  (the REST API + MQ/Kafka edge) and `payment-simulator-service` (test tooling). The
  Ingress (`k8s/base/ingress.yaml`) routes external traffic to exactly these two, by
  path (`/api/payments`, `/api/repair` → gateway; `/api/simulate` → simulator). No other
  service has an Ingress rule, deliberately — there's nothing for external traffic to
  reach on them.
- **`ConfigMap.temporal-target`** (`temporal-frontend.temporal.svc.cluster.local:7233`)
  is the one address every workflow/activity service actually dials. If you're
  wondering "how does X reach Y," the honest answer for 15 of these 17 services is
  "it doesn't reach Y directly at all — it reaches Temporal, and Temporal reaches
  whichever pod is free."

The exceptions, where a service genuinely does make an outbound HTTP call to another
system: `enrichment-activity-service` calls out to your internal Customer/Account
services (not part of this platform); `payment-gateway-service`/`payment-simulator-service`
receive real inbound HTTP. Everything else is Temporal-mediated.

## 4. What the decomposition exposed: RepairActivities' hidden coupling

Worth calling out explicitly, since it's a good example of what splitting a monolith
into services is *for*: the original `RepairActivitiesImpl.requalify()` called
`EnrichmentActivities`/`MopActivities` **as plain in-process Java objects** — that only
worked because they were beans in the same JVM. Once enrichment and MOP derivation are
separate services, that call is impossible (an activity implementation has no
Temporal execution context, so it can't create an activity stub to call another service
— only a *workflow* can). The fix: that orchestration moved to `RepairWorkflowImpl`,
which now calls `EnrichmentActivities` and `MopActivities` as two more ordinary
cross-service activity stubs, exactly like every other workflow already does.
`RepairActivitiesImpl` shrank to the one thing that's genuinely local: patching in the
operator's corrected fields. Arguably this is the more correct design even without a
microservices requirement — an activity silently calling another activity's Java
implementation was a blurred boundary that should have been explicit in the workflow
all along.

## 5. Identifier strategy — unchanged, still the same UETR-based scheme

Same design as the monolith: **UETR = the root workflow's Temporal workflow ID**,
generated at ingestion if the source lacked one. Every child workflow ID is namespaced
off it (`{uetr}-qualification`, `{uetr}-mop`, `{uetr}-repair-{n}`, `{uetr}-processing`),
and every child-workflow-stub / activity-stub call now *also* specifies the target
service's task queue explicitly (`ChildWorkflowOptions.setTaskQueue(TaskQueues.X)` /
`ActivityOptions` via `WorkflowSupport.activityOptions(TaskQueues.X)`) — the one thing
that's new versus the monolith, where a single shared task queue made this implicit.
Async correlation IDs (`{targetWorkflowId}::{suffix}`) work exactly as before.

## 6. Building

**payment-common first** — every service depends on it:

```bash
mvn -pl payment-common install     # or just `mvn install` at the repo root; the
                                    # reactor resolves build order automatically
```

**Building one service's Docker image** (from the repo root, not the service directory
— see the comment at the top of each generated Dockerfile for why):

```bash
docker build -f services/payment-processing-workflow-service/Dockerfile \
  -t payment-processing-workflow-service:local .
```

**Speeding up local builds**: each service's Dockerfile currently does its own
`mvn -am package` inside the build stage, re-resolving `payment-common` every time with
no shared cache. For anything beyond occasional local builds, either (a) add a
`RUN --mount=type=cache,target=/root/.m2` to the Dockerfiles (BuildKit cache mount), or
(b) do what a real CI pipeline should do anyway: publish `payment-common` to your
internal Maven repo (Nexus/Artifactory/GitHub Packages) as its own release step, so each
service's build only needs its own directory as context and a plain `mvn package` — no
whole-monorepo build context required. The generated Dockerfiles use the monorepo-context
approach because it's guaranteed to work without assuming you have a Nexus reachable
from this sandbox; swap it once you do.

## 7. Running locally

```bash
docker compose up -d --build
```

24 containers: 6 infra (Mongo, Redis, RabbitMQ, ActiveMQ, Kafka, Temporal+UI) + 17
services. Gateway on `localhost:8090`, simulator on `localhost:8091`, Temporal UI on
`localhost:8081`.

```bash
# Same walkthrough as the monolith README, just against the gateway's own port:
curl -X POST http://localhost:8091/api/simulate/inbound/MT
curl http://localhost:8090/api/payments/{uetr}
curl http://localhost:8090/api/payments/{uetr}/audit
```

## 8. Deploying to Kubernetes

```bash
kubectl apply -k k8s/base
```

This applies, in order: the `payment-platform` namespace, `ConfigMap`/`Secret`
(placeholders — see the comment in `secret.yaml` about using a real secret manager),
the `Ingress`, baseline `NetworkPolicy`, and all 17 services' `Deployment` + `Service` +
`HorizontalPodAutoscaler`.

**Before applying for real**:
- Set real image references: `k8s/base/kustomization.yaml`'s `images:` list currently
  points `REPLACE_WITH_YOUR_REGISTRY/<service>` at tag `1.0.0` for every service — push
  your built images there first, or edit the list (or use
  `kustomize edit set image <service>=<registry>/<service>:<tag>` per service).
  Deployments deliberately don't use Helm templating (`{{ }}`) — this is a plain
  Kustomize base, and per-environment differences belong in a Kustomize overlay (a
  `k8s/overlays/prod/` with patches), not hand-edited base YAML. None exists yet in
  this repo; add one when you have a second environment to actually diff against.
- Point `ConfigMap.temporal-target` at your real Temporal deployment (the placeholder
  assumes the official Temporal Helm chart in a `temporal` namespace).
- Match the `NetworkPolicy` namespace selectors (`ingress-nginx`, `monitoring`) to your
  actual ingress-controller and Prometheus namespaces.
- `payment-simulator-service` is test/sandbox tooling — either don't include it in a
  production deploy at all, or set its replica count to 0 via an overlay.

**Autoscaling note**: the generated `HorizontalPodAutoscaler` per service scales on CPU
(70% target). That's a reasonable default but not the most meaningful signal for a
Temporal worker — a worker can sit CPU-idle while its task queue backs up if its
per-worker concurrency limit is too low. Once you have Temporal/Prometheus queue-depth
metrics wired up, a KEDA `ScaledObject` on schedule-to-start latency per task queue is a
better trigger than CPU; the HPA here is the starting point, not the final word.

## 9. Known simplifications (same spirit as the monolith's "Known gaps")

- **`payment-common` bundles the Mongo and Redis drivers for every service**, even ones
  that never touch either (translation, enrichment, MOP, value-date, warehouse, all six
  workflow services). Each generated `application.yml` explicitly disables the
  corresponding Spring Boot autoconfiguration (`spring.autoconfigure.exclude`) via the
  manifest's `uses_mongo`/`uses_redis` flags, so an unrelated Mongo/Redis outage doesn't
  falsely fail those services' `/actuator/health`. The stricter fix — splitting
  `payment-common` into `payment-common-core` + optional `payment-common-mongo` /
  `payment-common-redis` modules so the *dependency* isn't there at all, not just the
  autoconfiguration — is the natural next step if image size or attack surface matters
  more than this exercise had room for.
- **17 services is a lot of operational surface for one payment pipeline.** This is
  what was asked for, and there's a real argument for it (independent scaling of
  partner-activity-service under partner-check load vs. warehouse-workflow-service,
  which is mostly idle timers, is exactly the win). But it's fair to note the
  middle-ground alternative: grouping the six low-traffic, single-replica activities
  (`value-date`, `mop`, `repair-activity`, `reversal`) into one small "misc-activities"
  service would cut the operational count from 17 to ~14 with little scaling downside,
  since none of them need independent scaling in practice (see each one's `replicas: 1`
  in `services.yaml`). Worth revisiting once you have real traffic data telling you
  which services actually need to scale independently and which were split more out of
  architectural purity than necessity.
- Every "Known gap" from the monolith README still applies verbatim (translator
  compliance, stubbed enrichment/reversal integrations, hardcoded MOP rules, no
  authN/authZ, no DLT handling, native-image being unverified for Temporal specifically)
  — none of that changed by moving code into more processes.
